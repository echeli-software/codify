# 11 — Internationalization

Two layers of translation: **app chrome** (UI strings) and **content** (lessons, courses, plans, etc.).

## 1. Locales

| Locale | Status | Notes |
|---|---|---|
| `pt-BR` | Primary | Default; strongest tone polish |
| `en-US` | Launch | Required for international users |
| `es-419` | Backlog | Spanish (Latin America); deferred until a Spanish-market commitment lands |
| `pt-PT` | Optional | Diverges from pt-BR in vocabulary; consider only if demand |
| Hebrew (`he-IL`) | Test-only | Used to verify RTL plumbing; not user-facing |

BCP-47 codes throughout. New locales added by:
1. Adding to the supported list in `libs/i18n`.
2. Translating chrome strings.
3. Activating in admin settings (so users can pick it).

## 2. Chrome translation: ngx-translate

Setup in `libs/i18n/provideI18n.ts`:
- `TranslateModule.forRoot({ loader, missingHandler, defaultLanguage: 'pt-BR' })`.
- Loader fetches JSON from `/i18n/<locale>/<chunk>.json` chunked per route group (lazy).
- Missing handler logs to Sentry in prod, warns in dev, returns the key.

### Key namespaces

| Namespace | Owned by | Examples |
|---|---|---|
| `common.*` | `libs/i18n` | `common.save`, `common.cancel`, `common.error.unknown` |
| `gamification.*` | `libs/i18n` | `gamification.xp.label`, `gamification.streak.daysOne`, `gamification.streak.daysOther` |
| `time.*` | `libs/i18n` | `time.relative.minutes` (with ICU plural) |
| `billing.*` | `libs/i18n` | `billing.installments.format` |
| `admin.*` | admin app | Per-screen subkeys |
| `student.*` | student app | Per-screen subkeys |

### Key conventions
- snake-free; dot-namespaced.
- ICU MessageFormat for plurals/genders. Example:
  ```
  "streak.days": "{count, plural, =0 {Sem ofensiva} one {1 dia} other {{count} dias}}"
  ```
- Never concatenate translated strings; always one key per phrase.
- Variables are explicit and documented in a sibling `.notes.md` for translators.

### Per-route lazy loading
- Each app's route module declares which chunks it needs.
- A small chunk-prefetch hint loads the next likely chunk on idle.

### Storage layout
```
apps/admin/src/i18n/
├── pt-BR/
│   ├── common.json     (re-exported from libs/i18n via build-time merge)
│   ├── courses.json
│   ├── plans.json
│   └── ...
└── en-US/
    └── ...
apps/student/src/i18n/
├── pt-BR/
│   ├── common.json
│   ├── today.json
│   ├── lesson.json
│   └── ...
└── en-US/...
```

Build merges `libs/i18n/strings/<locale>/*` into each app's chunks so shared keys live in one place.

## 3. Content translation

Lessons, courses, modules, categories, plans, badges, items, item categories, quest templates have user-facing fields. Stored in the `ContentTranslation` table per `(entityType, entityId, locale, field)`.

### Resolution order
1. Requested locale.
2. Course `sourceLocale`.
3. App default locale (`pt-BR`).

If we fall back to a non-requested locale, the response includes a header `X-Translation-Fallback: <fromLocale>` and the student app surfaces a one-time toast: "This lesson hasn't been translated to [locale] yet."

### Fetch pattern
The course/lesson API endpoints accept `?locale=<code>&fallback=true|false`. Default fallback `true`. Translations embedded in the response payload, not fetched separately:

```json
{
  "id": "...",
  "slug": "react-fundamentals",
  "title": "Fundamentos de React",
  "description": "...",
  "_translation": { "locale": "pt-BR", "source": "pt-BR" }
}
```

### Editor flow (admin)
- Side-by-side pane: source locale on the left (read-only), target on the right.
- Per-field "outdated" indicator if source updated after last translation.
- For `Lesson.contentJson`: opens the Tiptap editor pre-populated with the source doc; translator edits text in place. The doc structure is locked (no add/remove blocks).
- "Mark complete" persists and clears outdated flag for that field.

### Bulk import/export
- CSV per entity type with columns `entityId, locale, field, sourceValue, translatedValue`.
- JSON for translators using TMS tools.

## 4. Locale-aware formatting

### Currency
- `Intl.NumberFormat` per locale.
- pt-BR: `R$ 39,90`, `R$ 1.234,56`.
- en-US: `$9.99`, `$1,234.56`.
- Money values stored as `Int` cents + currency code.

### Dates & times
- `Intl.DateTimeFormat`.
- Relative dates: a small helper using `Intl.RelativeTimeFormat`.
- Time zone: respect `User.timezone`.

### Numbers
- Decimal & thousands separators per locale via Intl.

### Plurals
- ICU MessageFormat in chrome strings (ngx-translate-messageformat-compiler).

### Sort & collation
- For lists sorted alphabetically by user-facing strings, use `Intl.Collator` per locale.

## 5. RTL

We architect for RTL even though we have no production RTL locale on launch. Cost of doing this from day one is small; cost of retrofitting later is large.

- **No** hardcoded `left/right` in SCSS. Use logical properties (`inset-inline-start`, `margin-inline-end`, `padding-inline`).
- Bootstrap RTL CSS bundle imported when locale is RTL.
- Ionic supports `dir="rtl"` natively.
- Icons that imply direction (chevrons, back arrows) flipped per `dir`.
- Hebrew test locale (`he-IL`) added in non-prod to verify; CI screenshot test on a sample of pages.

## 6. Locale detection & switching

- On first visit, detect from `navigator.language` (web) or device locale (Capacitor).
- Persist user choice on `User.locale` once authenticated; thereafter, server-derived.
- Switch locale anywhere via `LanguageSwitcher` molecule. Updates:
  - ngx-translate language.
  - `<html lang>` and `dir` attributes.
  - User preference (server).
  - Refetches content responses with new `?locale`.

### Timezone
- On first sign-in, `User.timezone` is set from `Intl.DateTimeFormat().resolvedOptions().timeZone`. Streak attribution and quest scheduling depend on this.
- User-overridable in Settings → Account.
- Default `America/Sao_Paulo` only used until detection runs.

## 7. Tone & cultural adaptation

- pt-BR: warmer, uses humor and second-person familiar (`você`).
- en-US: concise, outcome-oriented, friendly.
- Avoid English idioms in source content; prefer plain language so translation stays clean.
- Local cultural touches: Brazilian holidays trigger themed shop drops and limited badges. Equivalents for other locales added when those markets warrant it.

## 8. Asset localization

- Course covers, badges, item thumbnails generally are language-agnostic.
- For assets that contain text (rare; we discourage), provide per-locale variants via the asset metadata (`{ assets: { 'pt-BR': '...', 'en-US': '...' } }`).
- Currency icon (Real, Dollar) handled by formatter, not asset.

## 9. SEO & marketing surfaces

(Out of scope for app v1, but the model accommodates.)
- Marketing pages render with `lang` + `hreflang` tags.
- Course pages have `<link rel="alternate" hreflang="x">` per available locale.

## 10. Pluralization corners

- Streak day strings are tested with 0/1/many.
- Currency `R$ 0,00` properly formatted (some libs return `R$ -0,00` for negatives near zero — handled with explicit tests).
- Relative time around boundary ("now", "in a moment", "yesterday").

## 11. Quality gates

- Lint rule: no string literals in templates (`*.html` and `.ts` template strings) — must come through `t()` or `{{ key | t }}`. Allowlist for non-user-facing strings via comment hint `// i18n-ignore`.
- Build fails if any user-facing component has a key with no entry in the default locale.
- A "translation completeness" report per locale is exposed in admin and visible to ops.
